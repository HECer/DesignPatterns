Learn design patterns – all 44 patterns at a glance

In short: This free learning tool explains all 23 Gang-of-Four design patterns plus 21 modern patterns (concurrency, enterprise architecture, cloud resilience) – each with intent, real-world analogy, when-to-use criteria, pros and cons and one complete code example in both C# and Python. A total of 44 patterns, 88 code examples, 5 interactive live demos, bilingual English/German.

Creational Patterns (9 – Gang of Four)

  • Singleton – Ensures a class has exactly one instance – with a global access point.
  • Factory Method – Defines an interface for creating objects, but lets subclasses decide which class to instantiate.
  • Abstract Factory – Creates entire families of related objects without naming their concrete classes.
  • Builder – Builds complex objects step by step – same construction steps, different representations.
  • Prototype – Creates new objects by cloning existing instances – instead of expensive re-construction.
  • Object Pool – Keeps expensive objects in a pool and lends them out instead of constantly creating new ones.
  • Lazy Initialization – Creates an object or value only when it is actually needed for the first time.
  • Multiton – Like Singleton – but with exactly one instance per key (e.g. per tenant or region).
  • Dependency Injection – Objects receive their dependencies from outside instead of creating them themselves.

Structural Patterns (7 – Gang of Four)

  • Adapter – Translates an existing interface into the one the client expects.
  • Bridge – Separates abstraction and implementation so both can vary independently.
  • Composite – Treats individual objects and object groups (trees) completely uniformly.
  • Decorator – Adds new capabilities to objects at runtime – by wrapping instead of inheriting.
  • Facade – Provides a simple interface to a complex subsystem.
  • Flyweight – Shares common state between thousands of objects to save massive amounts of memory.
  • Proxy – A surrogate controls access to the real object – for caching, protection or lazy loading.

Behavioral Patterns (13 – Gang of Four)

  • Chain of Responsibility – Passes a request along a chain of handlers until one processes it.
  • Command – Wraps an action as an object – so it can be stored, delayed and undone.
  • Interpreter – Defines a grammar for a small language and evaluates sentences of that language.
  • Iterator – Traverses a collection element by element without exposing its internal structure.
  • Mediator – A mediator centralizes communication of many objects – instead of everyone talking to everyone.
  • Memento – Stores snapshots of object state – for undo, without exposing internals.
  • Observer – Objects subscribe to events and are notified automatically when something changes.
  • State – An object changes its behavior when its internal state changes – without if cascades.
  • Strategy – Encapsulates interchangeable algorithms behind an interface – selectable at runtime.
  • Template Method – Defines the skeleton of an algorithm – subclasses fill in individual steps.
  • Visitor – Adds new operations to an object structure without changing its classes.
  • Null Object – Replaces null with a neutral object with "do nothing" behavior – no more null checks.
  • Specification – Wraps business rules as combinable objects: rule1.And(rule2).Or(rule3).

Concurrency Patterns (5)

  • Producer-Consumer – Decouples producers and processors via a thread-safe queue.
  • Thread Pool – Reuses a fixed group of threads for many small tasks.
  • Future / Promise – A placeholder for a result that will only be ready in the future.
  • Read-Write Lock – Many may read simultaneously – but only one may write exclusively.
  • Double-Checked Locking – Checks a condition twice – before and after the lock – to avoid expensive locking.

Architectural & Enterprise (7)

  • MVC (Model-View-Controller) – Separates data (model), presentation (view) and control (controller) into three roles.
  • MVVM (Model-View-ViewModel) – The view binds to a view model via data binding – ideal for modern UI frameworks.
  • Repository – Encapsulates data access behind a collection-like interface.
  • Unit of Work – Collects all changes of a business action and writes them in one transaction.
  • Publish-Subscribe – Senders publish messages to topics – receivers subscribe to topics. They never know each other.
  • CQRS – Strictly separates write operations (commands) from read operations (queries).
  • Event Sourcing – Stores not the current state but all events that led to it.

Resilience & Cloud (3)

  • Retry (mit Backoff) – Automatically repeats failed calls – with growing wait times.
  • Circuit Breaker – A fuse for service calls: after too many failures, the circuit opens.
  • Saga – Distributed transactions as a chain of local steps – with compensation instead of rollback.

Frequently asked questions about design patterns (FAQ)

What is a design pattern?

A design pattern is a proven, reusable solution template for a recurring problem in software design. Patterns are not ready-made code but a concept you adapt to your own situation – shown here with concrete examples in C# and Python.

How many design patterns are in the Gang of Four book?

The book "Design Patterns: Elements of Reusable Object-Oriented Software" (1994) by Gamma, Helm, Johnson and Vlissides describes exactly 23 patterns in three categories: 5 creational, 7 structural and 11 behavioral patterns. This site covers all 23 – plus 21 modern patterns beyond the GoF.

What categories of design patterns exist?

Classic: creational patterns (object creation, e.g. Singleton, Factory, Builder), structural patterns (object composition, e.g. Adapter, Decorator, Facade) and behavioral patterns (communication, e.g. Observer, Strategy, Command). Modern additions: concurrency patterns (Producer-Consumer, Thread Pool), architectural/enterprise patterns (MVC, Repository, CQRS) and resilience/cloud patterns (Circuit Breaker, Retry, Saga).

What is the difference between Strategy and State?

Both encapsulate behavior in interchangeable classes with the same structure. The difference is intent: with Strategy the client actively picks the algorithm (e.g. shipping method) and the strategies do not know each other. With State the object changes its own behavior when its internal state changes (e.g. order status), and states often define their mutual transitions.

Do design patterns differ between Python and C#?

The concepts are identical, the implementation differs: C# uses interfaces, events and language features like Lazy<T> or IEnumerable; Python solves much of it more lightweightly via duck typing, first-class functions, decorators, generators and modules. Some GoF patterns (e.g. Iterator, Strategy) are practically built into Python. That is exactly why this site shows every pattern in both languages side by side.
